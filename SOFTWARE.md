# Программная архитектура

Проект предоставляет ручное управление Roborock V1, текущий скан лидара,
телеметрию, камеру и отдельный аудиоконтур. Драйвером железа остаётся штатный
Player. Наш код работает на Linux-хосте; на роботе выполняются только
необходимые ARM-помощники.

ROS, DDS, TF, Nav2, RViz, Gazebo и wake word не используются. Лидарный
MRPT-SLAM подключается к серверной сессии; автономная поездка к цели
не реализована. Физические ограничения и правила работы с роботом
описаны в [HARDWARE.md](HARDWARE.md).

## Единая конфигурация

`bin/robot` читает `etc/robot.toml` из каталога репозитория независимо от
текущего рабочего каталога. Рабочий файл содержит секреты: только обычный файл
владельца с правами **0600**, без symlink; он исключён из Git. Публичный шаблон —
[`etc/robot.example.toml`](etc/robot.example.toml), с пустыми ключами.
Приоритет настроек: аргументы CLI → переменные окружения → TOML → встроенные
значения. Относительные пути в TOML отсчитываются от каталога самого файла.

Разделы: `[robot]` — SSH и Player; `[server]` — HTTP; `[supervisor]` — адрес,
порт, heartbeat, общий токен и ARM-бинарник; `[run]` — адаптеры SLAM/YOLO
(пустая строка отключает адаптер), `record_dir` — новый каталог единой
записи сессии (пустая строка отключает); `[camera]` — URL и netrc;
`[audio]` — громкость, предел и необязательный JSON-профиль;
`[yandex]` — `enabled`, `api_key`, `url`, `voice`, `folder_id`.
Другие ключи можно хранить в `[providers]`, например `openrouter_api_key`:
аудиоадаптер OpenRouter читает этот ключ без отдельного файла секрета.
Наличие ключа само по себе не включает облачный TTS: нужен `yandex.enabled = true`.

```sh
bin/robot run                              # настройки из etc/robot.toml
bin/robot --config /private/robot.toml run  # другой приватный TOML
bin/robot --config /private/robot.toml say 'Привет'
```

Старые аргументы запуска остаются как явные переопределения. `robot audio …
--config FILE` по-прежнему выбирает прежний JSON-профиль аудиосервиса;
общий TOML для этих команд задаётся **перед** `audio`. Настройки камеры и
громкости также применяются к snapshot/record и старому аудиосервису; явный
JSON-профиль переопределяет его значения по умолчанию.

### Озвучивание панели и CLI

Панель и `robot say` используют один HTTP API хостового `robot-server`:
`POST /api/audio/say` с `{text, volume?}` возвращает `202` и идентификатор
задания, `GET /api/audio/tasks/{id}` — его состояние,
`POST /api/audio/tasks/{id}/cancel` — запрос отмены. Успех означает только
состояние `completed`; принятие задания и запрос отмены ещё не подтверждают
завершение. Одновременно выполняется одно задание, повтор после потери связи
автоматически не запускается. `GET /api/audio/config` возвращает только
доступность, громкость и её предел, никогда не ключи.

Синтез Yandex выполняется на хосте. Ключ не попадает ни в браузер, ни на робот.
Готовый WAV передаётся аутентифицированному `robot-supervisor` по TCP.
Громкость по умолчанию 0.35, предел 0.9; обе настройки берутся из TOML.
Адрес API для `robot say` по умолчанию следует `[server]`; для удалённого
хоста можно отдельно задать `audio.endpoint`.

На роботе для этого пути нужен **один бинарник** `robot-supervisor`.
Он запускает тот же ELF в аудиорежиме; отдельный `robot-audio` не устанавливается.
Внутренний guard/worker сохраняет изоляцию ALSA и восстановление микшера.
Аудио не активирует маску устройств и не отключает штатный контроллер.

```sh
bash tools/build-supervisor.sh   # только локальная ARM/glibc-сборка
# Следующая команда меняет файлы на роботе; запускать только явно разрешённо:
bin/robot daemon start
bin/robot serve                  # HTTP/TTS без подключения к Player и без handoff
# В другом терминале, пока serve или run работает:
bin/robot say 'Проверка динамика'
```

Для обычной панели достаточно одной команды **`bin/robot run`**: она сама
сравнивает SHA-256 запущенного супервизора с локальным ARM-бинарником,
при необходимости обновляет свободный процесс, затем выполняет handoff
и запускает хостовый сервер с панелью и TTS. Отдельный `daemon start` перед
`run` не требуется, в том числе после перезагрузки робота. Одинаковый бинарник
переиспользуется без перезапуска и загрузки. Локальный исполняемый ARM-файл
обязателен даже при работающем сервере; сборка — `bash tools/build-supervisor.sh`.
Приведённая выше пара `daemon start` / `serve` нужна только для отдельного
HTTP/TTS-режима без управления шасси. `serve` и `run` не нужно запускать
одновременно на одном HTTP-порту. Старые флаги `robot say
--yandex-env` и `--piper-module-path` удалены: выбор и ключи провайдера теперь
на стороне сервера. Отдельный Python-аудиосервис остаётся для прежних функций
захвата/ASR и не требуется для TTS панели.

## Процессы и связи

```text
Браузер: React
    │ HTTP / WebSocket / MJPEG, порт 8085
    ▼
robot-server: Rust, рабочая машина
    ├── Player TCP :6665 ↔ Player на роботе ↔ LDS / шасси
    ├── heartbeat / WAV / cancel TCP :7665 → robot-supervisor на роботе
    ├── Yandex SpeechKit ← задания TTS панели и robot say
    ├── HTTP /mjpeg ← majestic на OpenIPC-камере
    └── опциональный YOLO-адаптер: JPEG по stdio → SSH gpu → YOLOE-26
        └── JPEG + объекты → отдельный /vision/ws → оверлей камеры

Python: robot audio run, отдельный запуск
    ├── локальный HTTP IPC :8086 ← команды audio CLI
    ├── HTTP /audio.opus ← majestic
    ├── pipes ↔ дочерний ffmpeg: Opus → PCM
    └── SSH / PCM → robot-audio guard → playback worker → ALSA / динамик
```

Все порты приведены для конфигурации по умолчанию. `robot-server` и
аудиосервис — независимые процессы: панель не запускает аудио автоматически.
На роботе и камере ROS нет.

| Компонент | Граница и ответственность |
| --- | --- |
| `bin/robot` | Короткоживущий CLI или shell-обёртка надзорной сессии: SSH, блокировка, запуск сервера, восстановление контроллера. |
| `robot-server` | Один процесс с Player-клиентом, HTTP/WS, прокси камеры и состоянием панели. Чтение Player, отправка скоростей и heartbeat выполняются независимо. |
| Браузер | React и Canvas. Веб-сервер Node.js при обычной работе не нужен. |
| `robot-supervisor` | Постоянный сервер на роботе: аутентификация, эксклюзивная сессия маски/heartbeat и независимое аудио. При потере владельца восстанавливает контроллер, но продолжает слушать. |
| `robotctl` | Прямой TCP-клиент Player для отдельных команд и показаний, не постоянно работающий сервер. |
| `mask-owner hold` | Альтернативное низкоуровневое владение маской с guard. Не дополнительный процесс рядом с активным `robot-supervisor`. |
| Python-аудиосервис | `AudioService` и `AudioRuntime` в одном процессе с рабочими потоками; ffmpeg — отдельный дочерний процесс. |
| `robot-audio` | ARM-помощник на время воспроизведения: родительский guard и дочерний ALSA worker. |

## Организация кода

* [`crates/player-bridge/`](crates/player-bridge/) — протокол Player,
  декодирование датчиков, CLI `robotctl`, ограниченные команды привода
  с latest-only слотом и сроком действия. Библиотека не зависит от веб-сервера
  или аудио; старые BackOff и StallDetector удалены.
* [`crates/robot-server/src/`](crates/robot-server/src/):
  `main.rs` — HTTP/WS, heartbeat и жизненный цикл;
  `recovery.rs` — общий для панели/MCP ограниченный операторский откат,
  контроль актуальности датчиков/владельца и отмена через супервизор;
  `player.rs` — асинхронный TCP, подписки и отправка скорости;
  `safety.rs` — владение ручным управлением и защитные состояния;
  `state.rs` — типизированное состояние сервера с разделами телеметрии,
  SLAM, компаса, моторов и блокировки; каждый производитель обновляет только
  свой раздел, а JSON-кадр панели собирается на границе (`State::to_json`);
  `telemetry.rs` — JSON и точки лидара; `camera.rs` — MJPEG-прокси;
  `vision.rs` — независимый YOLO-процесс и синхронный канал кадра с объектами.
* [`crates/mask-owner/`](crates/mask-owner/) — ARM-бинарники `mask-owner`
  и `robot-supervisor`, FIFO-протокол, локальный откат и
  `controller-restore.sh`.
* [`tools/panel-ui/`](tools/panel-ui/) — исходники и тесты React-панели.
  Результат сборки — один [`web/panel.html`](web/panel.html), который
  Rust-сервер читает с диска. Установку следует сохранять вместе с репозиторием.
* [`python/robot_audio/`](python/robot_audio/) — аудиоядро и native HTTP IPC.
  Основные модули: `capture`, `speech`, `runtime`, `service`, `playback`,
  `say`, `tts`, `policy`, `camera_session`.
* [`bin/audio/`](bin/audio/) — Python CLI и C-помощник динамика;
  [`bin/camera/snapshot`](bin/camera/snapshot) — отдельный снимок камеры.
* [`bin/owner/`](bin/owner/) — низкоуровневый C-код протокола маски,
  проверяемый офлайн-тестами.
* [`tools/yolo/`](tools/yolo/) — stdio-адаптер YOLOE-26, GPU-worker,
  явная подготовка модели и офлайн-тесты протокола.
* [`bin/bug`](bin/bug) — GitLab CLI; не часть управляющего процесса робота.

## Жизненный цикл серверной сессии

`bin/robot run`, `panel` и `bridge` запускают одну и ту же надзорную сессию.
По умолчанию подключаются лидарный MRPT-SLAM через
`tools/mrpt-adapter/adapter` и распознавание объектов через `tools/yolo/adapter`:
панель получает позу, карту и объекты поверх камеры. MRPT должен быть собран,
а GPU-окружение YOLO подготовлено заранее (см. README обоих адаптеров).
Отсутствие исполняемых файлов проверяется до SSH и передачи управления роботом.
`ROBOT_SLAM_ADAPTER` / `--slam-adapter EXE` и `ROBOT_YOLO_ADAPTER` /
`--yolo-adapter EXE` переопределяют пути; CLI имеет приоритет над окружением.
`--no-slam` и `--no-yolo` независимо отключают соответствующий контур.
`panel` не является пассивным просмотрщиком уже запущенного сервера.

1. CLI проверяет аргументы, наличие бинарника и локальную блокировку
   единственной сессии. Ошибка до передачи управления не меняет контроллер.
2. Разрешает настроенный SSH-алиас и проверяет `robot-supervisor` через `AUTH`
   и `PING`. PID определяется по слушающему сокету, с проверкой пути ELF;
   сравнивается `/proc/<pid>/exe`, а не только файл на диске. Одинаковая версия
   переиспользуется. Если порт не слушает, CLI загружает ARM-бинарник и скрипт
   восстановления. Если свободный сервер устарел, новый бинарник сначала
   загружается в отдельный файл с SHA-256 в имени и проверяется, затем старый
   процесс останавливается и файл атомарно заменяется. После запуска снова
   проверяются аутентификация и хеш. Активная сессия, отказ аутентификации,
   неизвестный процесс, занятость или ошибка загрузки/запуска останавливают
   `run` до handoff, без изменения контроллера.
3. Снимает штатный `RoboController` и запускает `robot-server`.
4. Сервер отправляет супервизору `ACTIVATE`, затем heartbeat раз в секунду.
   Начальное подключение и подписки Player имеют общий бюджет 10 секунд;
   отказ TCP-порта повторяется каждые 200 мс. Heartbeat во время ожидания
   не блокируется. DATA до ответов на подписки обрабатываются сразу теми же
   обработчиками, что и рабочий поток: сохраняются переходы бампера, начальные
   показания, история одометрии и время фактического приёма. Общей очереди
   стартовых DATA и лимита в 128 сообщений нет; остаются ограничение пакета
   1 MiB, ограниченная история и latest-only каналы скана/SLAM. После подписок
   используется тот же обработчик без сброса состояния или нумерации сканов.
   Ошибка протокола не повторяется.
5. После готовности Player сервер открывает HTTP и принимает браузерные
   подключения. Просмотр сам по себе не задаёт скорость.
6. При завершении, ошибке или потере установленного соединения сервер
   прекращает источники команд и пытается отправить нулевую скорость.
   Автоматического переподключения к Player и возобновления движения нет.
7. Супервизор выполняет локальное восстановление; CLI проверяет состояние
   контроллера и при необходимости вызывает восстановление дополнительно.
   Неуспешное завершение сервера не маскируется успешным cleanup.

### Автоматическое обновление супервизора

Обычный путь обновления — аутентифицированная команда `SHUTDOWN`:
`STOPPING` выдаётся только при отсутствии владельца маски, незавершённого
отката и других клиентов. Перед окончательной проверкой сервер закрывает
приём новых команд; `BUSY` не прерывает текущую работу. Остановка свободного
супервизора сама по себе не меняет маску и не восстанавливает контроллер.

Для прежней версии без `SHUTDOWN` предусмотрена миграция: updater удерживает
все 32 её клиентских слота после `AUTH`, проверяет, что следующий клиент
отклонён, и только тогда отправляет `SIGTERM` проверенному PID. Это исключает
новую `ACTIVATE` между проверкой свободного состояния и остановкой. Чужой
клиент, другое число слотов или нестандартный короткий таймаут запрещают
такую миграцию. Бюджет резервирования — менее 3 с при таймауте клиента
не менее 10 с; после повторной проверки PID/ELF бюджет проверяется ещё раз.

Параллельные обновления защищены каталогом `/tmp/mask-owner/update.lock`.
Он удаляется при обычном завершении и ошибке; после жёсткого обрыва может
остаться и блокировать следующие обновления. Такой остаток требует проверки,
а не автоматического удаления. Если новая версия не запустилась, `run`
не передаёт управление: штатный контроллер к этому моменту ещё не изменён.
`panel` и `bridge` используют тот же путь; `daemon start` также обновляет
свободный сервер, но не прерывает активную сессию. Автоматической пересборки
ARM-бинарника нет: сравнивается выбранный `ROBOT_SUPERVISOR_BIN` из конфигурации.
Изменившийся скрипт восстановления устанавливается при первичном развёртывании;
обновление бинарника сохраняет уже установленный скрипт.

Закрытие страницы не завершает серверную сессию. Потеря соединения
управляющего браузера сбрасывает его команду, но процесс и супервизор остаются
до завершения команды запуска. После живой сессии проверяют `bin/robot status`:
ожидается `enabled`.

### Ограничения команд

Пределы `0.5 м/с` и `3.14 рад/с`, срок команды `1 с` и семантика latest-only
заданы в коде привода. Потолки соответствуют ранее прочитанным
`max_speed 0.5` и `max_yaw_speed 3.14` штатного драйвера, а не измеренному
физическому максимуму.
Слайдер «Скорость» задаёт 0.01–0.5 м/с (начальное значение 0.1 м/с),
отдельный слайдер «Поворот» — 0.01–3.14 рад/с (начальное значение 0.4 рад/с).
Настройки независимы: изменение линейной скорости не меняет поворот.
Изменение регуляторов в покое не отправляет команд движения; при удержании
клавиши новая настройка применяется очередной отправкой (период 150 мс).
После настройки слайдера WASD работает и при оставшемся на нём фокусе,
а стрелки сохраняют стандартное управление самим слайдером. Прямая команда
`robot move` по-прежнему использует 0.1 м/с. Очередь старых скоростей не
проигрывается после задержки.
Период обработки команд сервера — 20 мс; молчание Player не блокирует этот таймер.

Ручным управлением владеет один WS-клиент. Подключение или отключение
наблюдателя не посылает команд. Отключение владельца останавливает его
управление. При переходе бампера «свободен → нажат» сервер устанавливает
`blocked=true`, удаляет ожидающую команду движения и запрашивает нулевую
скорость **только колёс**. Маска устройств, LDS, камера, вентилятор, щётки
и аудио при этом не меняются. Стоп имеет приоритет над новыми командами,
даже если сброс пришёл до очередного 20-мс цикла отправки скорости.

Пока `blocked=true`, обычное движение не принимается. В панели постоянно видно
уведомление «Наезд на препятствие» с кнопками «Отъехать назад» и «Сброс».
«Отъехать назад» — отдельный ограниченный операторский импульс, не обычная
команда WASD: −0.1 м/с прямо назад на 300 мс через локальный дедлайн супервизора.
Сервер допускает 1..500 мс на запрос и до 1000 мс на защёлку, требует свежих
кадров bumper/cliff/drop, запрещает текущий или защёлкнутый обрыв/отрыв.
Каждый клик — отдельный запрос, без автоматических повторов; отказ виден
в уведомлении. Потеря владельца/данных или новая опасность запрашивает STOP.
Подробные ограничения и аппаратная непроверенность — в HARDWARE.md.

Сброс — строгое
WS-сообщение `{"type":"reset_blocked"}`; результат немедленно рассылается
всем панелям как `state.data.blocked=false`, без ожидания новой телеметрии.
Отпускание бампера, команда ноль, отключение/подключение браузера и время
сами по себе блокировку не снимают. Сброс не забирает владение приводом
и не восстанавливает старую скорость. Удерживаемые клавиши в панели
очищаются: после сброса нужна новая команда, не автоповтор старой клавиши.

#### Моторы уборки

WebSocket-команда `{"type":"motors","fan":N,"main":N,"side":N}` управляет
вентилятором и щётками через интерфейс vendor `motor:170` (PWM, один XDR
float; индексы 0/1/2). Значения ограничены 0..=100, нечисловые отвергаются.
Командовать моторами может только владелец ручного управления; отключение
владельца и завершение сессии отправляют нули всем трём моторам.
Подписки на `motor:0/1/2` никогда не создаются: vendor ставит ноль в очередь
при отписке последнего клиента, а очередь не гарантирует отмену. Состояние
`state.motors` отражает запрошенные значения, не подтверждённые обороты;
телеметрия тока/статуса остаётся в служебных каналах `ir:6/7/8`.

Сброс отказан, пока бампер нажат или cliff/drop активен; во время
операторского отката он также запрещён. После освобождения датчиков и
сброса новое нажатие снова защёлкивает блокировку. Старые блокировки по
`stalled`, задержка 10 с, автоматический отъезд и запрет движения по
вердикту SLAM удалены. Операторский откат — новый явный ограниченный путь,
не восстановление старого автоматического BackOff. SLAM и одометрия — телеметрия; ограничения скорости,
lease 1 с, единственный владелец и остановка при его отключении сохранены.
Программный сброс `blocked` не сбрасывает ошибки MCU; физические ограничения
описаны в [HARDWARE.md](HARDWARE.md).

## SLAM: данные, качество и задержка

Построение карты использует MRPT `CICP` с явными XY-точками реальных лучей.
Это устраняет потерю одиночных лучей на стыке разреженного углового скана и
внутреннего фильтра `CMetricMapBuilderICP`. Для occupancy grid неизвестные
угловые сектора остаются невалидными; сетка пополняется инкрементально
доверенными keyframes, а не пересобирается из всей истории при экспорте.

Настройки `[slam]` в общем TOML задают ICP, пороги вставки, разрешение grid,
таймаут адаптера, максимальный возраст позы и допустимое рассогласование
одометрии. `source_time_verified=false` по умолчанию: сохраняются исходные
метки и монотонное время приёма, но время Player не объявляется временем
физического измерения. При явно подтверждённых часах доступна интерполяция
SE(2) в ограниченной истории; иначе используется ограниченная по возрасту
receive-order ассоциация с пометкой `unverified`. Отсутствующая одометрия
вызывает явную ошибку SLAM, а не фиктивное нулевое движение.

У обработчика один ожидающий последний скан и один в обработке. Пропущенное
перемещение сохраняется абсолютной одометрией относительно последнего
подтверждённого обновления. Чтение/запись адаптера ограничены общим бюджетом
(по умолчанию 1500 мс), ответ — 4 MiB. Неопределённый транспортный результат
не повторяется: worker сообщает ошибку и требует явного перезапуска сессии.

`state.slam` содержит реальные `diagnostics`, `tracking`, `error`, исходные
`scan_id`/`scan_stamp`, серверный `scan_sequence`, `age_ms`, `max_age_ms`,
`stale`, `dropped_scans`, метод/сдвиг одометрии и статус deskew. `scan.sequence`
позволяет сопоставить результат со сканом даже при повторении vendor ID и
метки времени. Повтор обычной телеметрии не омолаживает старую оценку.
Mapping `quality` — фактический goodness либо `null`, не постоянная 1.0;
MCL spread-прокси хранится отдельно в `localization_quality`.

Показатели ICP остаются в телеметрии. Панель удерживает последнюю согласованную
пару скана и позы, пока следующий результат в пути, но скрывает устаревшее
или ошибочное наложение. Переключатель системы координат даёт
диагностический вид неподвижной карты: старые occupancy-данные можно увидеть
отдельно, но скан и робот в мировой системе рисуются только при согласованной
позе. Пустые/недостающие CSV-клетки не превращаются в свободное пространство.

Времена лучей подтверждены моделью слотов и измеренным периодом оборота
(см. PLAYER_TIMING.md): рабочий deskew реализован в пути Player через SE(2)
ядро с плечом LDS. Он включается только явными флагами верификации
(`source_time_verified`, `beam_time_verified`, `deskew_enabled`), по
умолчанию выключен и телеметрия честно сообщает `applied`, измеренный
`period_ms` и причину любой деградации. Явно заданное окружение имеет
приоритет над TOML. На живой проверке у угла медианная ошибка стен при
вращении ±0.4…±1.44 рад/с снизилась с 79 до 34 мм.
Для некомпенсированных кадров большое приращение (по умолчанию более 0.08 м
или 8° между обработанными кадрами) приостанавливает пополнение карты и
опорного облака, не ограничивая колёса и не останавливая ICP. Это защита от
дальнейшего загрязнения карты, а не исправление исходного искажённого скана.

Протокол/сборка: [`tools/mrpt-adapter/README.md`](tools/mrpt-adapter/README.md).
Воспроизведение и численные результаты, включая нерешённые rolling-случаи:
[`tools/slam-replay/README.md`](tools/slam-replay/README.md).
Неподвижные аппаратные проверки 2026-10-29, исправление XDR-интенсивностей,
формат пассивного захвата `[slam].record_path` / `ROBOT_SLAM_RECORD_PATH`
и оставшиеся ограничения описаны в
[`PLAYER_TIMING.md`](tools/slam-replay/PLAYER_TIMING.md). Последующий
разрешённый физический прогон с поворотами до 1.44 рад/с и прямым ходом
до 0.2 м/с записан без потерь; он выявил рассогласование направлений
лидарной оценки и одометрии. Временная модель deskew пока не подтверждена.

### Единая запись прогона

```sh
bin/robot run --no-yolo --record-dir /private/existing-parent/new-session
```

Это обычная живая сессия, не подключение к чужому серверу. Параметр также
доступен как `[run].record_dir` / `ROBOT_SESSION_RECORD_DIR`, по умолчанию пуст.
Каталог должен быть новым; существующие цели отвергаются до handoff,
серверная проверка без symlink выполняется до ACTIVATE. Файлы приватны.

В bundle входят `player.jsonl` (все входящие сообщения единственного Player-
клиента), выборки состояний и сканов, входящие команды колёс/сброса,
JPEG-кадры камеры и `manifest.json`. Команда в журнале — запрос, не
доказательство принятия или физического движения. Все времена приёма/выборки
используют общую монотонную шкалу; это не времена экспозиции или измерений.
Карта не копируется в каждое состояние. Запись ограничена очередями,
размерами и временем, её диск/камера не блокируют привод или heartbeat.

Недоступная камера не мешает записи датчиков, но в manifest будет
`camera.status=unavailable`, а общий `complete=false`; сырые датчики имеют
собственный результат полноты. JPEG захватываются отдельным HTTP-потоком
через существующий безопасный camera-клиент, не вторым Player-подключением.
`ROBOT_SLAM_RECORD_PATH` и единая запись одновременно не задаются.
Подробные ограничения и разбор:
[`tools/session-recording/README.md`](tools/session-recording/README.md).

Сервер отправляет JSON-кадры `{"type":"state","data":...}`,
`{"type":"scan","data":...}` и `{"type":"map","data":{"version":N,"grid":...}}`.
Карта SLAM передаётся отдельным версионируемым кадром только при изменении
grid и повторно при новом подключении; частые кадры состояния и обновления
возраста SLAM не пересылают неизменившуюся карту, а `state.slam` ссылается
на неё полем `map_version`. При подключении также приходит
`{"type":"vision","data":{"enabled":true|false}}` — настройка видеоканала,
без JPEG в управляющем сокете. Команда браузера — `{"v":0.05,"w":0}`:
линейная скорость в м/с, угловая в рад/с. Некорректные и нечисловые значения
не превращаются в задания приводу.

Состояние содержит одометрию и инвентарь `sensors`: батарею, док (`dock` —
факт зарядки из power-кадра; отдельного датчика дока на проводе нет), бампер
(агрегат плюс флаги сегментов Left/Front/Right в `bumper_segments`), ИК
стены/обрыва/отрыва, сырые массивы, сонар и магнитометр (`compass` —
отдельный read-only поток сырых ST480, не yaw из `position3d:2`;
каноническое расположение — `sensors.compass`, дублирующее поле верхнего
уровня `compass` удалено как не имевшее потребителей). Неизвестные
значения остаются `null`, а не нулями. Это последние полученные данные,
не гарантия физической свежести каждого датчика.

Данные `sensors.service_channels` (`ir:3/4/6/7/8`, `position3d:0/1/2/4`)
остаются в протоколе, но на панели не отображаются. Гироскоп и одометрия
показываются отдельными приборами; служебные подписки необязательны:
NACK не мешает запуску сервера.

Панель использует всю высоту и ширину viewport через сетку `#root`:
карта и лидар занимают правую колонку, камера и компактная панель датчиков —
левую колонку одинаковой ширины. Числовые значения компаса скрыты, его
графический прибор сохранён; отсутствие эха сонара обозначается ∞. Сонар
отображается отдельным виджетом, ИК-каналы — индикаторами наличия данных:
их цвет не является признаком безопасного пола или состояния препятствий.
Отдельного раздела SLAM нет: слои «Скан лидара» и «Карта SLAM» включаются
чекбоксами в заголовке лидара; диагностика SLAM остаётся только в WS-состоянии.
Управление движением и моторами уборки — в нижней панели.
Развёрнутая панель занимает только рабочую область, не перекрывая footer.
На очень маленьких экранах доступна внутренняя прокрутка датчиков.
Компас получает отдельное аутентифицированное подключение к
`ROBOT_SUPERVISOR_ADDR` (обычный `bin/robot run` задаёт его автоматически).
После `AUTH` команда `COMPASS` передаёт не чаще 10 Гц строки
`COMPASS <stamp> <raw_x> <raw_y> <raw_z>`. Это независимый наблюдатель:
нет `ACTIVATE`, захвата evdev, команд движения или восстановления контроллера.
Супервизор проверяет имя устройства `compass`, при необходимости находит его
через sysfs. Метка — время исходного `SYN_REPORT`, не объявленное UTC.

Сервер отдаёт `source:"st480-evdev"`, `frame:"sensor"`, `calibrated:false`,
сырые целые x/y/z и `yaw=atan2(y,x)` — **угол магнитного поля в плоскости
датчика**, не курс робота и не север. Отображение явно подписано «Без
калибровки · оси датчика». Нулевые X и Y не задают направление; yaw тогда
`null`. Реальный угол 0° при ненулевом горизонтальном поле допустим.

Статус рабочего потока — `uncalibrated`. При отсутствии новых меток более
секунды — `stale`, ошибках данных — `invalid`, недоступном устройстве —
`unavailable`; yaw становится `null`. Повтор старой метки не продлевает
свежесть. Потерянное соединение закрывается; повторное подключение только
наблюдателя выполняется через 2 с и не затрагивает привод. Браузер отдельно
скрывает показание через 1.5 с без новой метки либо сразу при потере WebSocket;
другие кадры телеметрии и раскрытие панели не обновляют возраст компаса.

Прежний супервизор отвечает `REFUSED`: панель показывает «Обновите
супервизор», а не неподвижную стрелку. Для нового источника нужны свежие
хостовый `robot-server`, bundle и ARM `robot-supervisor`; локальная сборка —
`cargo build --manifest-path crates/Cargo.toml -p robot-server --release`,
`npm --prefix tools/panel-ui run build`, `bash tools/build-supervisor.sh`.
Следующий разрешённый `robot run` автоматически обновит устаревший свободный
супервизор по описанному выше протоколу. До подтверждённой остановки старого
процесса его ELF не заменяется; при активной сессии обновление запрещено. Пороговый vendor `position3d:2` остаётся только в
служебной телеметрии и не может заменить или затереть магнитное измерение.

Гироскоп показывает **поворот в плоскости пола, вид сверху**, используя
`position3d:0 pos[5]` (относительный yaw). Крен и тангаж не управляют
графикой; рядом указана угловая скорость `vel[5]`. Это относительный
гирокурс, не магнитный север. Авиагоризонт и сырая строка гироскопа убраны.
При отсутствии yaw изображение направления не рисуется.

Одометрия `state.odom` вынесена в два отдельных прибора рядом с компасом
и гироскопом: положение X/Y со стрелкой курса и измеренные скорости v/ω.
Старая числовая полоска под лидаром убрана. Схема положения показывает
локальное смещение от нуля одометрии с автоматически подобранной шкалой,
а не карту или траекторию SLAM. Два индикатора скоростей имеют независимые
шкалы ±0.5 м/с и ±3.14 рад/с; графика ограничена шкалой, числовое измерение
не обрезается. Неизвестные значения не подставляются нулями.

`keypad:0` и `motor:0/1/2` перечислены в панели, но автоматическая подписка
на них отключена: формат vendor-keypad не подтверждён, а жизненный цикл
vendor-motor может влиять на привод. Для этих строк прямо указана причина
отсутствия данных. Панель не посылает им команд и не меняет маску устройств.

Скан содержит `points`, `range_max`, `frame: "base_link"` и, при корректной
исходной метке, `stamp` Player. Используются направления отдельных лучей
и перенос начала LDS на x=-0.100 м. Установочный yaw уже включён vendor-
драйвером в опубликованные направления; сервер повторно его не добавляет.
Метку Player нельзя автоматически
считать Unix-временем. Одометрия показывается как телеметрия и не перемещает
точки по карте. В Canvas X направлен вправо, Y вверх; робот остаётся в начале
координат, если пользователь не сдвинул обзор.

Камера получает Basic credentials на стороне сервера из приватного netrc.
Они не попадают в URL браузера, WS или ответы прокси. Прокси не следует за
редиректом с авторизацией. Сервер проверяет браузерный WS Origin, но это
не заменяет аутентификацию или сетевое ограничение доступа.

## Распознавание объектов YOLOE-26

Обычный запуск включает оба адаптера:

```sh
bin/robot run
# Эквивалентно явному выбору:
bin/robot run --slam-adapter tools/mrpt-adapter/adapter --yolo-adapter tools/yolo/adapter
# Отключить только распознавание, оставить карту:
bin/robot run --no-yolo
# Обычная камера без обоих адаптеров:
bin/robot run --no-slam --no-yolo
```

**Эти команды запускают обычную серверную сессию с передачей управления
контроллером**, а не пассивный просмотрщик. При `--no-yolo` GPU-процесс не
запускается и камера работает через прежний MJPEG-прокси. Без `--no-yolo`
используется YOLO-адаптер по умолчанию; `ROBOT_YOLO_ADAPTER` и
`--yolo-adapter EXE` переопределяют путь. Исполняемый файл проверяется до SSH
к роботу; готовность модели проверяется асинхронно и не задерживает
heartbeat/управление. YOLO не получает доступа к приводам. Прямой запуск
низкоуровневого `robot-server` по-прежнему включает YOLO только явным флагом.

Сервер открывает один поток камеры для распознавания, извлекает JPEG с
ограничением 2 МиБ и хранит только последний кадр. Адаптер получает
`{"op":"init"}`, затем `{"op":"detect","frame_id":N,"jpeg":"base64"}`;
ответ содержит тот же `frame_id`, размер исходного изображения, список
`objects` с `label`, `confidence`, нормализованным `box:[x1,y1,x2,y2]` и
`inference_ms`. Лимиты: 100 объектов, ответ 64 КиБ, init 180 с, запрос 30 с.
Камера, адаптер и видеосокет работают отдельно от Player и safety.

Панель использует `/vision/ws`: JPEG и рамки приходят одним сообщением,
новое изображение сначала декодируется, затем отображается вместе со
своими объектами. Это поток обработанных кадров, а не рамки поверх более
нового несинхронизированного видео. Пропорции сохраняются при разворачивании
панели. Ошибка/разрыв или отсутствие свежих результатов больше 3 с убирают
кадр и рамки; сбой YOLO не завершает управление роботом. Адаптер повторно
запускается с паузой 3 с. Сервер завершает локальный дочерний процесс при
остановке; после жёсткого обрыва SSH немедленная отмена GPU kernel не
гарантируется. Закрытие панели останавливает её видеосокет, но не выключает
серверное распознавание до завершения сессии.

По умолчанию `tools/yolo/adapter` передаёт только JPEG и конфигурацию по
`ssh gpu` в `~/robot-yolo/worker.py`, используя отдельный venv. Креды камеры
остаются у Rust-сервера. Используется `yoloe-26l-seg.pt` с явным indoor-списком
классов; выводятся рамки, подписи и уверенность (не маски и не расстояния).
Для тонких проводов и других мелких препятствий качество отдельно проверяется
на кадрах камеры; распознавание не является защитой от столкновений.

```sh
YOLO_CLASSES='["person","chair","shoe","cable","cat","dog"]' YOLO_CONF=0.3 \
  bin/robot run
```

Зависимости и веса устанавливаются **только явной подготовкой**, не при
`robot run`. Подробности, pinned-зависимости, локальный режим, протокол и
лицензия Ultralytics AGPL/Enterprise — в [tools/yolo/README.md](tools/yolo/README.md).
На GPU нужны готовые CUDA-wheel и совместимый драйвер, не nvcc/toolkit.

На RTX 3090 проверены реальные `init`/`detect`, соответствие `frame_id`,
размеров JPEG и координат объектов. Полный путь от локальных fake Player/камеры
через Rust и настоящий GPU-worker до оверлея проверен в браузере. Проверки
не выполняли передачу управления физическим роботом; качество indoor-детекции
на его камере отдельно не принято.

## Сборка и запуск

Для основного контура нужны Linux, Rust stable/Cargo, Bash, SSH, `timeout`
и `flock`. Для аудио — Python 3 и ffmpeg. Node.js/npm нужны только для
изменения и сборки UI.

```sh
cargo build --manifest-path crates/Cargo.toml --release
(cd crates && cargo build -p mask-owner --release --target armv7-unknown-linux-musleabihf)
```

Первая команда создаёт host-бинарники в `crates/target/release/`, вторая —
ARM-помощники. Кросс-конфигурация находится в
[`crates/.cargo/config.toml`](crates/.cargo/config.toml) и
[`tools/arm-lld.sh`](tools/arm-lld.sh). Сборка ничего не запускает на роботе.

Пересборка браузерной части:

```sh
(cd tools/panel-ui && npm ci && npm test -- --run && npm run build)
```

**Живая сессия: следующая команда снимает штатный контроллер и включает
необходимые устройства.**

```sh
bin/robot run
# http://127.0.0.1:8085
```

`--port` меняет HTTP-порт; `--listen` — адрес привязки. По умолчанию доступ
только через loopback. `--listen 0.0.0.0` допустим лишь в доверенной сети
или за отдельно настроенной защитой. `--slam` и `--sim` не поддерживаются.

CLI выбирает release-бинарник, затем debug. `ROBOT_SERVER_BIN` задаёт
явный путь; `ROBOT_SUPERVISOR_BIN` — ARM-супервизор для развёртывания;
`ROBOT_SESSION_LOCK` — локальный lock; `ROBOT_SSH` и `ROBOT_SSH_TIMEOUT_S` —
SSH-обёртку и её предел ожидания. `ROBOT_SERVER_HEARTBEAT` штатно задаёт CLI.

`robot-server --help` описывает низкоуровневые параметры Player и камеры.
Прямой запуск сервера не заменяет передачу владения контроллером и маской.
Для обычной работы используется `bin/robot run`.

Отдельные аппаратные команды доступны через `bin/robot --help`:
`status`, `enable`, `disable`, `position`, `battery`, `fan`, `stop`, `move`,
`mask`, `snapshot`. Они не должны конкурировать с активной серверной сессией.
`position` при завершении посылает нулевую скорость, поэтому для просмотра
положения во время движения используется телеметрия сервера. Команда `fan`
распознаётся CLI, но её получение в текущем Rust-клиенте не реализовано.

## Python-аудиоконтур

`AudioRuntime` объединяет один источник PCM, сеанс речи, очередь выхода и
политику mute/quiet hours. `AudioService` предоставляет к нему loopback HTTP;
CLI не использует ROS и не отправляет команды движения. Все источники,
распознавание и выход по умолчанию выключены. Модели не скачиваются автоматически.
Для локального ASR устанавливаются зависимости из
[`requirements-audio.txt`](requirements-audio.txt) в отдельное Python-окружение
и задаётся локальный путь модели в профиле. Piper устанавливается отдельно;
ему нужны подготовленные файлы голоса. Ни pip-установка, ни импорт модели
не являются проверкой реального микрофона.

```sh
bin/robot audio check-config --config config/audio.example.json
bin/robot audio run --config config/audio.example.json
bin/robot audio status
```

Пример профиля — [`config/audio.example.json`](config/audio.example.json).
Рабочий профиль хранится вне репозитория. `check-config` только проверяет
схему и лимиты. Сервис по умолчанию слушает `127.0.0.1:8086`; `run --port N`
и клиентский `--endpoint http://127.0.0.1:N` выбирают другой локальный порт.

* `capture.py` получает Opus камеры и декодирует его дочерним ffmpeg в
  PCM 16 кГц, mono, S16LE. Сервис делит один поток между записью и ASR.
* `speech.py` сегментирует явно начатую реплику и вызывает локальный ASR
  с ограничениями времени и длины. `audio start` начинает реплику,
  `audio status` показывает результат, `audio finish SESSION_ID` завершает
  соответствующую обработку ответа.
* `playback.py` управляет приватным asset-кешем, ограниченной очередью,
  отменой и SSH-транспортом. `say.py` и `tts.py` реализуют используемые
  локальные и облачные TTS-адаптеры. Облачные вызовы требуют явного согласия.
* `robot-audio` сохраняет микшер и воспроизводит PCM через guard/worker.
  BUSY не разрешает убивать чужой playback. Потеря связи оставляет исход
  неопределённым; повтор автоматически не запускается.

Wake word, его модели обучения/оценки и голосовое прерывание ответа удалены.
Старый раздел `wake` и удалённые флаги/команды отклоняются. Ручная реплика
не начинается во время динамика; сохраняется пауза после воспроизведения.
Опциональный AEC не следует считать подтверждённым голосовым barge-in.

### Команды аудио

```sh
bin/robot audio listen on
bin/robot audio record ./test.wav --seconds 6
bin/robot audio start
bin/robot audio import ./notification.wav --config ~/.config/robot/audio.json
bin/robot audio play ASSET_ID --volume 0.35 --ttl 5
bin/robot audio say 'Проверка динамика'
bin/robot audio stop
bin/robot audio mute on
```

Команды работают только с явно включёнными функциями профиля. `record`
использует сервисный поток; самостоятельный `bin/robot record` / `audio capture`
не требует сервиса. Готовый WAV создаётся с `0600`, без перезаписи; разрыв или
пропуск в незавершённой сервисной записи делает её недействительной.
`bin/robot say` также работает самостоятельно. Учтите аппаратные ограничения
усиления и акустики из [HARDWARE.md](HARDWARE.md).

IPC предоставляет `GET /status` и `POST /request` с JSON-объектом `command`.
Команды: `status`, `listen`, `mute`, `start`/`utterance`, `finish`, `record`,
`play`, `say`, `stop`. `listen`/`mute` используют `enabled`, `finish` —
`session_id`, отмена может указывать `task_id`. `record` возвращает WAV/base64;
CLI проверяет формат перед созданием файла. Размеры, длительности и число
задач ограничены. Результат playback означает исход выполнения, не просто
принятие запроса; неподтверждённая отмена не выдаётся за остановку.

Helper собирается локально:

```sh
bash bin/audio/build.sh --output ~/.cache/robot/build/robot-audio-arm
```

Отдельно разрешённое развёртывание: `bin/robot audio deploy --binary PATH --confirm`.
Оно меняет файл на роботе и не является частью обычного `audio run`.
`audio companion` — особый ограниченный режим камеры/маски; обычное аудио
его не требует. Не запускайте companion одновременно с серверной сессией.

## Разработка и диагностика

```sh
cargo fmt --manifest-path crates/Cargo.toml --all -- --check
cargo test --manifest-path crates/Cargo.toml --workspace
bash tests/test_robot.sh
bash tests/test_robot_camera.sh
bash tests/test_robot_owner.sh
python3 -m unittest discover -s tests -p 'test_*.py'
(cd tools/panel-ui && npm test -- --run)
shellcheck bin/robot bin/camera/snapshot bin/audio/build.sh tests/*.sh
```

Тесты сервера используют локальные Player, HTTP/WS и camera fixtures. Тесты
маски, контроллера и аудио используют фейки. Дополнительные протокольные
тесты умеют запускать локальный upstream Player из `~/.cache/robot/player`;
его подготовка необязательна для основного fake-контура. Тесты не подтверждают
физическое торможение, акустику или надёжность на реальном Wi-Fi. Правила TDD
и доступа к железу — в [CLAUDE.md](CLAUDE.md).

| Симптом | Что он означает |
| --- | --- |
| `waiting for Player` | После watchdog restart порт ещё не готов; действует ограниченное стартовое ожидание. |
| `Player startup timed out` | Подключение/подписки не завершились за 10 с; это ошибка сессии, не повод бесконечно переподключаться. |
| «Наезд на препятствие» | `blocked=true`: колёса остановлены до явного «Сброс»; отпускание бампера само по себе недостаточно. |
| «Нет данных» | Показание не получено или недостоверно; это не нулевая дистанция и не признак безопасности. |
| Нет камеры/звука | Проверяются питание, доступность, netrc и явно включённые функции профиля; режимы робота не меняются автоматически. |

Не открывайте управляющие порты в интернет. HTTP/Basic камеры не шифруется;
пароли находятся в приватном netrc, GitLab-токены — в игнорируемом `.env`.
Трекер вызывается только через `bin/robot bug`; правила русскоязычных задач
и обработки секретов описаны в [CLAUDE.md](CLAUDE.md).
