# LESSWRONG — журнал хода исследования платформы

Файл фиксирует, где исследование платформы Roborock V1 тратило усилия впустую, что из этого вышло полезного и что сделано иначе. Ведётся, чтобы не повторять уже пройденные круги. Дата нижеследующих событий: 2026-10-02 — 2026-10-03.

## Что делал предшественник (контекст до смены модели)

Цель пользователя: сначала закончить исследование платформы, затем строить `player_to_ros2` (тонкий Rust-мост). Необходимый физический минимум — движение с работающим LDS и выключенными обеими щётками. Архитектурный вывод, который нужно сохранять: управляем Player как есть, RoboController — образец штатного поведения и восстанавливается после испытаний, но не конкурирует за управление в рабочем контуре.

Предшественник продуктивно разобрал: внешний TCP API Player (`position2d:0`, `laser:0`, vendor `motor:0/1/2`), путь смены маски `0x04010045` → `RubyChassisDriver::ChangeDeviceState()`, поведение щёток (разрешения `0xb1` ≠ задания скорости `0xc3/0xc4`), STM32-уровень (общая линия PA11), живые проверки: изолированный PWM LDS не дал сканов; штатная уборка дала обороты LDS и сканы, но меняет сразу много состояний; щётки удалось наблюдать вращающимися через несколько секунд после старта уборки.

Затем началось топтание: всё более глубокое дизассемблирование `libroboipc.so` (каналы, sequence-счётчик, completion-пакеты `SendPacketEx`/`CompletePacket`/`pPostProcessPacket`, `GetProcIndex`). Каждая итерация давала новые факты о транспорте, но блокеры лежали не там:

1. **Работает ли LDS при выключенных щётках** — физический факт, из бинарника не вычисляется.
2. **Быстрый fail-stop при гибели владельца** — тоже физический факт.
3. Достаточность IPC-контракта **уже была достигнута** для написания fake-тестов; дальнейшая археология — убывающая отдача.

Урок: офлайн-исследование охотно заполняет время вместо физического рубежа, требующего отдельного разрешения. Нужно явно замораживать линию разбора и переходить к фейкам/живой сессии.

## Что сделано после (шаг 1, офлайн, 2026-10-03)

Диагноз топтания был согласован с пользователем, после чего закрыт ABI с другой стороны — не транспорт, а смысл полей:

- **Таблица битов `_Robot_DeviceBitmap`** из `BitmapToString()` (`RoboController 0x2e284–0x2e6f4`): 0=Bumper, 1=UltraSonic, 2=Cliff, 3=Compass, 4=Wall, 5=Drop, 6=Bin, 7=LDS, 8=LDS(f), 9=MainBrush, 10=SideBrush, 11=Fan, 12=Wheel, 13=Odometer, 14=Accelerator, 15=Gyroscope, 16=Incline, 17=Dock, 18=Battery, 20=Slam; биты 7/8 взаимоисключающие. Штатная маска уборки `0x10feff` декодируется таблицей полностью — перекрёстная проверка сошлась.
- **Карта ModuleID** из `GetProcIndex()` (`libroboipc 0x50b4`): 1=RoboController, 2=Navigation, 3=AppProxy, 4=McuProxy, 5=SysUpdate, 6=SysLog, 7=WatchDog, 8=WirelessManager, 9=SlamProxy, 10=LaserProxy, 11=CompassProxy; аббревиатуры `Rc/Nv/Ap/Mc` — суффиксы FIFO.
- **Wire-формат подтверждён трассой** (5 полных пар запрос/ответ): слово `+0` = event (LE, `0x0045`) + байты src/dst, `+4` = счётчик отправителя, `+8` = длина payload (4), `+12` = битмап; всего 76 байт. Запрос `Rc(1)→Mc(4)`, ответ — event `0x00a9`, `Mc(4)→Rc(1)`.
- **Правило корреляции закрыто**: `ChangeDeviceState()` отправляет одно событие и блокируется в `WaitForPriorityEvent(-1)`; ответ приходит через ~270 мс; порядковый номер в ответе — собственный счётчик Mc, не эхо запроса. Правило: один запрос в полёте, ждать `0xa9`; таймаут обязан обеспечить владелец (штатное ожидание бесконечно).
- Кандидаты обрели точный смысл: **`0x10f8ff` = уборка минус MainBrush(9)+SideBrush(10), LDS(bit7) остаётся включённым**; `0x10f0ff` — дополнительно без вентилятора. Оба по-прежнему не испытаны физически.

Транспортный раздел `docs/player-platform-survey.md` дополнен и **заморожен**: дальнейшее дизассемблирование транспорта не даёт ничего для физического рубежа.

Оба урока обязательны для репозитарной реализации владельца.

## Шаг 4 — репозитарный владелец маски на Rust (выполнен, 2026-10-03)

Кросс-компиляция: `armv7-unknown-linux-musleabihf` + `rust-lld` из тулчейна через shim `tools/arm-lld.sh` (срезает `-Wl,` и cc-флаги, которые голый lld не принимает); конфиг в `rust/.cargo/config.toml`. Статический бинарь, зависимостей нет. Смоук-тест на роботе прошёл.

Реализация `rust/mask-owner` (TDD):
- кодек `lib.rs` — юнит-тесты на реальных векторах трассы (запрос 0x36 и ACK 0x50);
- `ipc.rs` — канал `O_RDWR|O_NONBLOCK` на оба FIFO (урок живой сессии: после рестарта Player у McRc нет писателя, блокирующее открытие висит), дренаж посторонних пакетов до обмена, конечный таймаут обмена, ограничение пропуска посторонних;
- guard: форк ДО установки маски, слежение за владельцем через /proc с zombie-проверкой, stand-down маркер, восстановление standby 0x40 с 3 повторами;
- интеграционные тесты `tests/fifo.rs` на настоящих FIFO с фейковым Mc-пиром; e2e `tests/guard_e2e.rs` с настоящим бинарем: SIGKILL владельца → guard восстанавливает standby; SIGTERM → владелец сам восстанавливает и гасит guard маркером. Поймано и исправлено: двойной restore (main + Drop) — `restore()` сделан идемпотентным; тест-drain поймал, что FIFO-буфер отбрасывается ядром при закрытии последнего писателя (писатель должен жить во время чтения).

Обёртка `bin/robot mask hold|restore`: гейт «контроллер остановлен», валидация маски (ровно 6 hex-цифр), деплой бинаря по sha256, отдельные аргументы ssh-команды. Тесты обёртки расширили `tests/test_robot.sh`; ssh-фейк эмулирует удалённый exec бинаря. Поймано обёрткой в тестах: stdout функции деплоя замусоривался ответами ssh (command substitution) — теперь в stdout идёт только путь.

Не сделано: живая валидация репозитарного инструмента на роботе (шаг 5) — по отдельному разрешению.

## Шаг 5 — живая валидация репозитарного владельца (выполнена, 2026-10-03)

Пройдено живьём через `robot mask hold` (деплой по sha256, гейт контроллера):
- маска `0x10f8ff` применена, ACK, LDS ~30000; `laser:0` — **75 сканов за 15 с** (360 точек), щётки неподвижны (визуально);
- SIGTERM-откат: владелец сам восстановил standby, LDS=0, процессы ушли чисто;
- **две живые аварии guard пойманы и закрыты**:
  1. SIGHUP teardown ssh-сессии — guard теперь `setsid()` + ignore HUP/TERM/INT;
  2. **SIGPIPE от наследованной stderr-трубы** — корневая причина: ssh-канал владельца закрывается при его смерти, первая же запись guard в stderr убивала его до restore. Фикс: guard игнорирует SIGPIPE и отсоединяет stdio (лог в `/tmp/mask-owner-guard.log`, при невозможности открыть — `/dev/null`, logging никогда не должен убивать guard). Регрессионные e2e-тесты воспроизводят обе аварии локально (`guard_survives_session_teardown_sighup`, `guard_survives_closed_stderr_pipe`).
- после фикса живой `kill -9` владельца под ssh: guard пережил, `standby restore ACKed (attempt 1)`, LDS=0 за ~2 с. Побочно найдена и устранена утечка осиротевших owner/guard пар от оборванных тестовых сессий (мешали диагностике).
- e2e-тестирование само наступило на грабли: SIGHup группе тест-харнесса (владелец без собственной группы) — тест-процессы теперь в `process_group(0)`; и IO-safety double-close fd в тесте — лечится `mem::forget` обёртки сокета.
- Робот восстановлен: контроллер enabled, LDS 0, артефакты удалены. Все наборы зелёные (rust 5×ok, включая 2 новые регрессии; обёртка, player, camera, owner, bug; shellcheck).

## Шаг 6A — протокольное ядро player_to_ros2 (выполнен, 2026-10-03)

Решение по архитектуре: ROS-слой (rclrs/ros2_rust через colcon) — отдельный инкремент 6B; crates.io-заглушки вроде `sensor_msgs 0.0.0` не работают. Сначала ядро — чистый Rust, ноль зависимостей, чтобы кросс-сборка для робота была как у mask-owner.

Ground truth: **локальный Player-сервер** из дерева `~/Projects/robot/ros2/player` (dummy.cfg: laser:0 + position2d:0) на свободном порту; интеграционные тесты сами его поднимают (`rust/player-bridge/tests/against_server.rs`, skip при отсутствии дерева).

Реализовано в `rust/player-bridge` (TDD): 40-байтовый XDR-заголовок, баннер-хендшейк, подписка REQ_DEV, декод laser-скана и position2d-state, velocity-команды. Все 3 интеграционных теста + юнит-тест зелёные против настоящего сервера.

Два XDR-урока, стоившие часов:
1. **u8-поля живут в 4-байтовых XDR-слотах со значением в МЛАДШЕМ байте.** Я писал значение в старший байт слота; сервер декодировал type=0 и молча дропал сообщение («unsupported type unknown:0»). Python-пробы «работали» из-за перепутанных состояний сервера — NACK совпадает с ACK по длине. Спасло только снятие настоящего libplayerc-клиента tcpdump-ом и побайтовое сравнение дампов; ручной «эталон» из головы врал.
2. **xdr_array/xdr_bytes дублируют count**: перед данными массива идёт ещё один u32-счётчик (поле структуры + счётчик энкодера). Из-за него laser-декодер ошибался ровно на 4 байта; фактическая длина payload (1844) сошлась только при учёте обоих счётчиков у обоих массивов.

Мета-урок: три часа гаданий «почему сервер молчит» — то же топтание, против которого этот файл. Правило подтверждено и расширено: при расхождении клиентов **сразу** снимать эталонный дамп работающего клиента (оракул), а не перебирать гипотезы.

## Шаг 6B — ROS-слой player_to_ros2 (выполнен, 2026-10-04)

Пользователь поправил размещение: весь наш код — в `~/robot`. Пакет узла — `~/robot/ros2/player_to_ros2`, дерево Player (заголовки/сервер/протокольные исходники, 74M) перенесено в `~/robot/ros2/player`; colcon-workspace со сторонними клонами (ros2_rust, examples, common_interfaces...) остался внешним окружением в `~/Projects/robot/ros2/rust-ws`, наш пакет подключён туда симлинком.

Прояснено недоразумение: Player — не ROS 1, а отдельная middleware (Player/Stage), вендорски используемая прошивкой; наш новый код — чистый ROS 2 Jazzy.

Путь сборки (рабочий): colcon + `colcon-cargo`/`colcon-ros-cargo`, `Context::default_from_env()?.create_basic_executor()`, параметры через `declare_parameter("...").default(v).mandatory()?` → `.get()`. Сообщения — **`ros-env = "0.3"`** (`use ros_env::*`): крейт подхватывает rosidl-генерацию из sourced workspace. Ловушки: crates.io-имена `sensor_msgs`/`builtin_interfaces` — нерабочие заглушки (yanked), path-зависимости на сгенерированные крейты конфликтуют по `rosidl_runtime_rs` 0.6 vs 0.7 (генератор из клона пишет 0.6, rclrs 0.8 хочет 0.7). Всё это обходит ros-env одним шагом.

Узел (`ros2/player_to_ros2/src/main.rs`): поток-читатель Player (подписки laser:0 + position2d:0, между чтениями флаш `/cmd_vel`-команд), ROS-цикл публикует `/scan` (angle_min/max/increment, ranges, intensities) и `/odom` (поза + кватернион из yaw, twist). Параметры: player_host, player_port, laser_frame, odom_frame. Поймано живым прогоном: push-режим шлёт DATA раньше ACK на REQ_DEV — `subscribe` теперь пропускает DATA.

E2E против локального Player (dummy.cfg): `/scan` ~72 Гц (сервер 75), `/odom` ~12.5 Гц (сервер 10), `/cmd_vel` проходит до velocity-команды. `ros2 topic echo` показывает корректные поля. Все cargo-тесты зелёные.

Не сделано: прогон против живого робота (по разрешению), TF (пока только frame_id), Nav2. 

## Надзорная сессия моста (сделано, 2026-10-04)

Требование пользователя: запуск моста автоматически останавливает контроллер; смерть моста или потеря связи — останавливает робота и возвращает контроллер, надёжно.

Решение: **восстановитель живёт на роботе** (workstation не может отвечать за откат — она сама умирает). `robot-supervisor` (второй бинарь mask-owner, Rust/ARM-статик): слушает heartbeat-порт; `robot bridge` деплоит его, делает disable, запускает ROS-узел; узел шлёт байт/сек. EOF или тишина 5 с → полный откат локально: zero-velocity по loopback TCP (XDR CMD без подписки — проверено по playertcp: TCP-слой пушит CMD в очередь устройства без гейта), standby-маска по FIFO (второй, независимый путь остановки), затем `controller-restore.sh` (дословный перенос bash-enable без ssh, идемпотентен).

Контракт: без ACTIVATE supervisor тихо выходит ничего не трогая (упавший disable не оставляет опасного слушателя). Потеря heartbeat в мосте = выход моста (не шлём скорость из мёртвой сессии).

TDD: `tests/rollback.rs` (порядок zero-vel→маска→restore на фейках), `tests/supervisor_e2e.rs` (EOF, тишина, quiet-exit — настоящие бинари), обёртка в `test_robot.sh` (supervisor раньше disable, disable раньше узла). Поймано тестами: баннер фейка должен быть ровно 32 байта; subscribe не нужен для CMD; activation-окно параметризовано (10 с на роботе, 1 с в тесте).

## Этап 3: первая карта из живого движения (2026-10-04)

Живая сессия: `robot bridge` + медленные проезды (0.1 м/с, суммарно ~0.59 м + поворот 1.63 рад) с записью bag (573 скана, 5743 одометрии, TF). Сессия оборвалась преждевременно: watchdog перезапустил Player посреди езды (вероятная причина — поток connect/disconnect от robotctl-запросов; урок: команды в сессии должны идти через одно соединение моста, а не отдельными robotctl). Supervisor откатил штатно.

SLAM-пайплайн доведён до карты. Цепочка найденных и закрытых проблем (все — «загляни в данные, а не гадай»):
1. `set -u` + ROS setup.sh → unbound variable, дети пайплайна молча не стартовали (главная ловушка дня);
2. дефолт slam_toolbox `base_frame: base_footprint`, у нас `base_link`;
3. режим: сообщение «LocalizationSlamToolbox» сбивало с толку — реально нужен `mode: mapping` в конфиге;
4. bag-сканы имели нулевые штампы (мост записан до фикса штампов), а `latest_odom`-restamp в replay ломал таймлайн из-за пачечной доставки игрока;
5. **static base_link→laser в bag тоже был с нулевыми штампами** — невидимо ломал дерево TF при внешне корректном odom→base_link.

Решение: `scripts/stamp_bag.py` — одношаговая перештамповка bag'а временем записи (692 сообщения), затем прямой `ros2 bag play` → slam_toolbox без посредников. Итог: **карта сохранена** (110×89, 0.05 м/px, origin [-0.99,-0.34]). `scripts/slam-from-bag.sh` воспроизводит весь путь.

Открыто: мост должен штамповать static_tf (в коде сейчас default-stamp 0 — исправить при следующей правке моста); Player-рестарты при частых подключениях.

## Этап 3, часть 2: Nav2 офлайн на записанном bag'е (2026-10-04)

Полный навигационный стек поднят и валидирован на replay: `scripts/nav2-replay.sh` + `config/nav2_replay.yaml` — map_server + AMCL + costmaps + planner (NavFn) + controller (DWB) + collision_monitor + bt_navigator, `/cmd_vel` в файловый приёмник.

Результаты прогонов:
- **«Goal succeeded», error_code 0** для цели в отображённом коридоре;
- цель вне карты честно отвергнута («outside bounds»), цель в неизвестном пространстве — «Failed to create plan»: стек корректно отказывается, а не выдумывает маршрут;
- AMCL локализует на сохранённой карте (поза совпала с одометрией записи).

Грабли Jazzy-конфигурации (все закрыты): `dwb_core::DWBLocalPlanner` (не nav2_controller::DWBPlanner), `nav2_navfn_planner::NavfnPlanner` (:: не /), collision_monitor требует непустые polygons+sources с `polygon_sub_topic`, docking_server требует dock_plugins, дублирующийся ключ map_server в YAML молча съедал блок, `set -u`+ROS setup. Сим-время с bag --clock замораживает контейнер после конца bag'а — работает wall-time вариант.

Фундаментальное ограничение replay: AMCL в каждый момент видит позу из записи, поэтому controller считает цель достигнутой по факту записанного положения — ненулевые команды на replay не воспроизвести честно; это нормально, этап проверки реальных команд — живая поездка (этап 5 плана).

Правило на будущее: перед новым кругом дизассемблирования спрашивать, закрывает ли оно физический блокер; если нет — это топтание.
